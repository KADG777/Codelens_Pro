## 配对方法

- 模型：同一 DeepSeek 配置 `deepseek-flash`，温度 0.1，关闭推理模式，网络重试次数 0。
- 相同输入：逐任务使用同一自然语言需求、初始源码与验收合同。7 项上传修复/检查，1 项需求生成。
- 直接处理：一次模型推理，返回完整源码，无工具、审查、测试反馈或格式重试。
- 完整工作流：实际并行审查和独立验收、条件判断、最多两轮修复、验收解读 Agent；单任务最多 18 次调用、40,000 token、240 秒。上传入口按设计跳过编码；生成入口首稿正确时合法跳过修复。
- 奇偶任务交替两组执行次序。每对两份结果固定后，再执行独立公开及保留用例评分；保留用例从未进入 Agent 输入或用于修复。
- 成功：两组采用同一外部评分，公开和保留用例均实际执行且全部通过，并绑定最终源码 SHA-256。模型自述和工作流终态不能替代评分。
- 回归任务：上传前整体通过、输出后失败。回归用例：上传前通过的某个用例在输出后失败。没有初始源码的生成任务不计初稿回归。
- 时间：各处理组墙钟时间，包含工作流内部审查和验证；排除处理结束后的外部评分。不是仅模型延迟，也不是并行相对于顺序的加速实验。
- 保留所有预定项，包括预算耗尽、错误或未验证项；不能剔除失败后重算通过率。

已有任务：数值截断、区间合并、滑动平均、正确订单代码对照。新任务：循环右移、列表分块、游程解码、重叠子串计数。新任务是在这次工作流改动后新写、模型实验前冻结的合成任务；没有根据这些运行结果调整提示词或选择性补跑。它们不是外部独立作者提供的盲测集，也不能排除模型预训练已见过类似问题。

## 如何解读收益

当前证据支持“工作流提供了检查、修复和重新验收的可追溯过程”，不支持“多 Agent 比直接模型更准确”。简单纯函数上的一次强模型调用已经足够，工作流会产生较大额外成本。新增解读角色也有成本，本实验没有消融其贡献。

下一步应预先冻结更复杂任务，增加独立作者任务和重复次数，并比较“直接生成+相同检查工具”的基线、移除审查/解读角色的消融。先确定何时值得启用完整工作流，再考虑按风险选择轻量或完整路径。不得为了得到正收益而删除这次平局结果。
