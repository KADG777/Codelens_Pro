# 工作流成本与可靠性优化

## 结论与当前边界

此次修正了重复付费审查、缺少候选回归保护、协议纠错反馈不足，以及错误的模型预期能否决正确修复的问题。真实记录支持减少工程开销，但**没有证明 Multi-Agent 普遍比单 Agent 更准确或更便宜**。

对原有四类任务各重跑一次，全部通过公开与隐藏检查，共 17,012 token，平均 4,253 token / 任务；旧实验同四类任务共 12 次，平均 25,951.8 token / 任务。平均开销约减少 83.6%，但重复次数不同，不能据此推断成功率显著提高。

## 实际改动

1. **一次审查，重复执行证据**：需求核对与反例计划合并为一次结构化请求；格式错误最多纠正一次。源码改变后重跑保存的反例，通常不再调用审查模型。未知需求或未完成计划仍保留未知状态。
2. **候选采用前验证**：已经通过的独立冻结用例不能变成失败、缺失、跳过或错误。违反时保留当前源码，记录候选、SHA-256 和拒绝依据；成功检查按源码哈希复用。
3. **区分实际执行与正确预期**：WASI 执行能证明程序返回了什么，不能证明模型预期正确。模型反例只形成待核对意见；不进入自动修复目标，也不拥有候选否决权。
4. **减少交接与重试浪费**：源码与相同任务文本只发送一次，失败检查不重复展开；返回具体格式错误而非笼统重试。短中文引用有效，反例要求短输入与短预期。瞬态网络错误最多重试一次，每次重新检查并扣减调用和 token 预算。
5. **状态可见**：页面展示反例输入、实际结果、模型预期，以及是否重跑已有计划。拒绝候选与当前源码区分展示，历史策略仍可选。

精简策略适用于绑定 TaskSpec 的便携功能验收；无合同的静态任务保留原完整审查。标准库导入所需的隔离指令预算由 20 亿提高至 100 亿；256 MiB 内存限制和原有时限保留，避免将正常的 `urllib.parse` 导入误判为源码缺陷。

## 真实实验记录

原始数据均不覆盖，任务集的 16 条公开检查和 40 条隐藏检查在首次请求前冻结，并使用参考实现核对。两次完整试验均为 4 项内部合成任务 × 3 次重复 × 3 组，按轮换顺序执行。隐藏检查在三组候选固定后评分，未提供给 Agent。

### 第一轮优化

| 方法 | 独立评分通过 | token | 调用 | 耗时合计 |
|---|---:|---:|---:|---:|
| 直接处理 | 11/12 | 12,273 | 12 | 29.81 秒 |
| 单 Agent + 测试 | 12/12 | 12,212 | 12 | 44.31 秒 |
| Workflow | 8/12 | 50,419 | 27 | 184.41 秒 |

三个区间任务卡在结构化合同校验，一个窗口任务遇到连接超时；另有一次审查输出截断，虽然已有候选通过评分，流程仍中断。失败全部保留在 [首次优化原始报告](../evals/results/optimized-live.json)。原四任务回归也保存在该文件的 `diagnostics` 中。

### 协议修正后的同任务完整工程复测

| 方法 | 独立评分通过 | 已测回归用例 | token | 调用 | 耗时合计 |
|---|---:|---:|---:|---:|---:|
| 直接处理 | 11/12 | 0 | 12,441 | 12 | 29.85 秒 |
| 单 Agent + 测试 | 12/12 | 0 | 14,065 | 13 | 46.78 秒 |
| Workflow | 11/12 | 0 | 63,131 | 33 | 188.03 秒 |

这次是同任务工程复测，**不是新的盲测**。没有改任务或预期答案，也没有只补跑失败组。Workflow 正常完成公开验收的运行是 9/12，最终源码独立评分为 11/12，两项分别报告。中间组有 1/12 实际进入反馈修复。Workflow token 仍约为中间组的 4.49 倍。

唯一评分失败发生于窗口任务：对于 `events=[0,1,2], limit=2, window=2`，按合同在 t=2 时移除时间 <=0 的记录，正确结果是 `[true,true,true]`。模型却提出 `[true,true,false]`，原回归保护据此拒绝了正确候选。

完整记录：[工程复测原始报告](../evals/results/optimized-retest.json)。该文件通过 SHA-256 引用上一轮报告，保留两轮累计预算。

### 最终修正的定点验证

最终规则取消了模型预期的自动修改权和否决权：

- **零 API 回放**：使用上面被拒绝的原候选，按新规则成功采用，公开和隐藏检查全部通过，原运行记录未改动。
- **一次真实重跑**：同一窗口任务使用最终实现，正常完成并通过全部独立检查；额外 2 次调用、2,651 token。

这是针对唯一误拦截案例的事后验证，**不能合并成完整实验 12/12，也没有对最终实现再做整套新的盲测**。结果见 [最终规则验证](../evals/results/oracle-guard-check.json)。

原 10/12、311,422 token 的历史成绩仍保留在 [第三版实验](AGENT_VALUE_EXPERIMENT.md)。对不同任务集的 token 总数不做严格因果比较。

## 费用、复现与使用建议

全部新增实验及定点验证共 **119 次调用、184,204 已报告 token**；无用量返回的请求按预留额保守扣减，合计 **191,320 token**。用户授权初始为 120 次 / 200,000 token，后续只将调用上限调整至 140 次；token 上限始终未变。没有提交 API Key，CI 不运行真实模型实验。

`compare_optimized.py`、`compare_optimized.py --retest`、`verify_oracle_guard.py` 分别对应上述阶段，均拒绝覆盖已存在的报告。重新实验应使用独立输出和新的明确费用授权；不要删除原报告以筛选成绩。

简单、合同充分的任务中，现有数据支持单 Agent + 测试作为经济基线。需要交接追踪、独立检查、候选保护和故障恢复时，Workflow 提供这些工程能力，但必须同时展示其额外开销。四个内部合成任务与三次重复不足以证明外部项目上的泛化优势。
