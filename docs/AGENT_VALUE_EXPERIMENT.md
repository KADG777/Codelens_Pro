# Agent 协作价值：实验总览与历史记录

## 当前结论（第四版实现）

最新一轮完整工程复测中，直接处理通过 **11/12**，单 Agent + 测试通过 **12/12**，精简 Workflow 的最终源码独立评分通过 **11/12**。Workflow 正常完成公开验收的运行是 **9/12**，其余运行中的源码也接受独立评分；两种指标不能混用。三组均无已测用例回归。

| 方法 | 最终源码独立评分通过 | 已测回归用例 | 模型调用 | token | 处理耗时合计 |
|---|---:|---:|---:|---:|---:|
| 直接处理 | 11/12 | 0 | 12 | 12,441 | 29.85 秒 |
| 单 Agent + 测试 | 12/12 | 0 | 13 | 14,065 | 46.78 秒 |
| 精简 Workflow | 11/12 | 0 | 33 | 63,131 | 188.03 秒 |

该复测使用 4 个内部合成任务，每项重复 3 次，属于同任务工程复测。单 Agent 组有 1/12 实际进入反馈修复；Workflow 的 token 仍约为该组的 **4.49 倍**。当前证据支持减少重复审查、独立验收、交接追踪和恢复能力，**没有证明多 Agent 普遍更准确或更便宜**。

唯一评分失败来自错误的模型预期否决正确修复。最终规则已取消模型预期的自动修改权和否决权；原候选的零 API 回放和该任务的一次真实重跑均通过，后者使用 2 次调用、2,651 token。**这属于事后定点验证，不能把上表改成 12/12，也没有对最终规则再做整套新的盲测。**

## 第三版历史实验

以下保留第三版完整审查策略的原始协议、成绩和恢复探测；其中的 10/12 和费用不代表第四版精简策略。所有原始报告保持不变，失败结果也保留。

### 历史结论

这次实验没有证明多 Agent 比单 Agent 更准确。在 4 个新任务、每项 3 次重复中，直接处理通过 **11/12**，单 Agent 测试组通过 **12/12**，完整 Workflow 通过 **10/12**。完整工作流使用了更多 token 和时间，还出现了源码回归与 API 超时。因此，项目的实证价值是可审计的分工、独立验证与恢复机制；不能用这些数据宣传准确率优势。

### 历史冻结协议

任务集 [agent_value_cases.json](../evals/agent_value_cases.json) 在调用真实模型前保存。包含严格 CSV 解析、JSON 指针、依赖批次和事务转账四个任务，16 个公开检查、39 个隐藏检查。预先用确定性参考实现验证合同可满足。全部是内部新编写合成任务，不是外部盲测。

三组使用相同任务、原始缺陷代码、公开接口、DeepSeek 模型配置（`deepseek-flash`、温度 0.1）和独立评分器：

| 组 | 可使用的信息与动作 |
|---|---|
| 直接处理 | 一次生成完整源码，不接收测试反馈 |
| 单 Agent + 测试修复 | 同一 Agent 生成后运行公开检查，失败时最多修复两次 |
| 完整 Workflow | 审查与独立验收并行，必要时独立修复，再审查、再验收；最多修复两轮 |

工作流本次不启用可选的验收解读 Agent，以减少与正确性无关的解释开销。它仍包含原 CodeLens 审查角色内部的工具调用与反思，因此与单 Agent 组的提示、调用数量不完全相等，不能声称这是只改变“角色数”的严格因果实验。每组上限 18 次模型调用、40,000 token、240 秒；直接组仅一次推理，中间组最多三次推理。全实验上限 180 次调用、500,000 token，客户端关闭自动 HTTP 重试。

每项任务的三次重复轮换三组顺序，减少固定先后顺序影响。三组候选全部固定之后，才运行相同的公开及隐藏评分；隐藏反馈从不回传给模型。报告在开始前列出全部计划条目，失败、未执行及预算停止都保留，报告不能覆盖。

### 历史主实验结果

| 组 | 通过 / 计划 | 回归用例 | 调用次数 | token | 总耗时 |
|---|---:|---:|---:|---:|---:|
| 直接处理 | 11/12 | 0 | 12 | 14,570 | 34.03 秒 |
| 单 Agent + 测试修复 | 12/12 | 0 | 12 | 14,728 | 50.02 秒 |
| 完整 Workflow | 10/12 | 3 | 101 | 311,422 | 311.39 秒 |

耗时包含组内模型、工具和验收工作，不含三组共同的最终评分。回归按“原始代码原本通过的同一用例，最终候选变为失败”计算。完整工作流相对直接组没有独有成功；直接组独有成功 1 次。相对单 Agent 测试组，后者独有成功 2 次。

**中间组本次全部首稿通过公开检查，没有实际触发反馈修复。** 它与直接组的差异可能来自模型采样，不能把 12/12 与 11/12 的差异归因于反馈机制。这项控制组的工具能力已实现并测试，但本次数据未充分触发它。

四个任务分别保留三次结果，不把 12 次运行当作 12 个独立任务，不给出暗示大样本独立性的置信区间。CSV 首次 Workflow 出现隐藏用例回归并耗尽单任务预算；依赖批次首次 Workflow 在修复节点遭遇 API 连接超时，最终候选仍为原代码。这两项都计入失败。

完整原始结果、源码、评分、用量及 12 次源码哈希交接记录见 [agent-value-live.json](../evals/results/agent-value-live.json)。第一轮 8/8 对 8/8 的报告也保持不变：[首轮配对实验](PAIRED_COMPARISON.md)。

### 历史实验的单独真实恢复探测

主实验结束后，对上述 API 超时的依赖批次运行执行 **一次继续**，使用原 SQLite 检查点与现有预算，未新建任务或重跑已成功的前置检查。

- 状态：`blocked → completed_verified`。
- 从原失败的 `fix` 节点继续，旧交接记录的 ID 和内容保留。
- 新版本再次审查及验收，恢复后公开和隐藏评分均通过。
- 额外 4 次模型调用、10,652 token。
- 主实验分数仍然是 10/12；该次事后恢复不并入主表，也不作为整体恢复成功率。

原始记录：[real-recovery.json](../evals/results/real-recovery.json)。加上这次探测，总计 **129 次调用、351,372 实际 token**；保守预算计费为 368,748 token，包含未返回完整用量时的预留扣减，未超出授权上限。

这提供了一个真实失败后从保存状态继续的例子。另有零 API 调用的 [故障注入记录](../evals/results/recovery-probes.json)，检查并行分支故障、服务重开、成功分支不重复与同哈希重试；两种证据分开展示。

以下命令复现第三版完整审查策略；第四版实验入口见上文链接。已有报告不能覆盖。配置本机环境变量后，可使用新报告路径运行：


运行会调用模型并产生费用。任务集与实现文件 SHA-256 保存于报告；实际模型服务、负载、缓存和网络变化可能影响结果。本次运行的模型执行路径采用标准并行模板，画布调度机制由单独的自动化和界面测试验证。

后续应由外部人员提供未参与开发的任务，冻结新协议，并加入更能触发公开反馈修复的任务，以及同调用 / token 预算的消融组。优先考察“失败是否能定位并恢复”和“每次成功成本”，而不是按已有结果挑选有利任务。当前数据也提示：简单任务应优先考虑成本较低的直接处理或单 Agent 方式；完整 Workflow 更适合需要责任分工、检查点和交接证据的场景。
