## 验证层级

| 证据 | 可以说明 | 不能说明 |
|---|---|---|
| 模拟模型与状态测试 | 固定输入下交接、恢复、错误和预算行为符合断言 | 真实模型稳定识别所有问题 |
| AST / Ruff | 已配置静态规则和语法条件满足 | 业务行为正确、程序已经运行 |
| 订单演示 | 固定角色产物可以走完整流程并产生真实文本差异 | LLM 编码或修复准确率 |
| 隔离功能验收 | 当前哈希源码通过实际执行的冻结用例 | 所有输入、所有业务和宿主环境均正确 |

`static_only` 下 `functional_executed` 必须为 false，最终显示静态完成。`functional_portable` 使用附带并校验哈希的 CPython WASI，支持 10 个注册纯函数合同；`functional_required` 保留 Docker 订单验收。环境不可用应报告阻塞，不能把“未执行”计为“通过”，也不静默降级为静态验收。模型不能修改用于验收的用例。

Docker 是可选执行能力，便携功能验收和静态验证无需它。若选择 Docker 功能验收，需要安装并启动 Docker Desktop，然后在终端预先准备镜像：

```powershell
docker pull python:3.11-slim
docker image inspect python:3.11-slim
```

首次拉取需要网络，应用不会自动下载镜像。Docker 档的内置订单验收冻结了空输入、混合付款状态、零金额、缺失字段、负数、布尔金额、错误 paid 类型和非字典订单等用例，并检查不修改输入。其他注册合同使用便携档；不能把订单测试套用到其他函数冒充覆盖。

Docker 档的候选源码只在容器中运行，默认容器禁网、只读、非 root、限制 CPU/内存/进程数量，并设置测试超时。具体参数见 `workflow/validation.py`。这些限制服务于本地课程 MVP，不构成对任意恶意代码的完整隔离证明；不要用宿主机直接执行源码来绕过环境不可用。
